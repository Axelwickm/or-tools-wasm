ROOT CAUSE CONFIRMED (follow-up investigation)

This is an Emscripten JSPI pthread lifetime race, naturally exposed by the
observed WebKit scheduling. It is not evidence of an Atomics.waitAsync
implementation defect in WebKit. No actual Apple Safari execution has yet
been tested. The earlier mailbox fallback is a workaround, not the root fix.

Causal chain:
1. invokeEntryPoint resets runtimeKeepaliveCounter=0 and noExitRuntime=0,
   invokes the pthread through WebAssembly.promising, and awaits its result.
   It does not retain the runtime across that await.
2. A resolved mailbox wait can run checkMailbox during that interval.
   In particular, a callback from a previous use of the pooled worker can
   observe the new pthread identity. checkMailbox uses callUserCallback.
3. callUserCallback unconditionally invokes maybeExit in its finally block.
   With no keepalive, maybeExit calls _emscripten_thread_exit prematurely.
4. C teardown clears pthread_self and publishes DT_EXITED, permitting the
   main runtime to join/free the pthread and recycle its worker.
5. The suspended invokeEntryPoint resumes and calls finish, attempting
   another _emscripten_thread_exit. It can act on no current pthread.
   With assertions disabled, this invalid teardown can leave the program
   hanging. Full downstream memory-corruption consequences were not audited.

Evidence:
- Bounded-join reproduction of the natural WebKit failure captured a worker:
    before await: pthread_self=70176
    mailbox callback: pthread_self=70176
    after mailbox callback: pthread_self=0
    after await: pthread_self=0
- The timed join returned ETIMEDOUT (73) for an unfinished thread.
- Scheduling queueMicrotask(checkMailbox) before the pthread entry promise
  continuation forces this ordering in Chromium too. Uncorrected run hung
  at iteration 1. This is explicit test fault scheduling, not a claim that
  ordinary Chromium execution reliably reproduces the race.
- With ASSERTIONS=1, forced ordering produced:
    Assertion failed: self, pthread_create.c:312, _emscripten_thread_exit
  Stack: finish -> invokeEntryPoint -> handleMessage.
- Balanced runtimeKeepalivePush/Pop around the pending JSPI entry fixes the
  isolated test: 1000 natural WebKit iterations and 1000 forced-ordering
  Chromium iterations passed. Neither waitAsync nor JSPI was disabled.
- All solver groups/executor modes in Vite dev WebKit passed with that
  correction applied by a diagnostic response transform: 1 passed (1.6m).
- Pure JavaScript mailbox/Promise tests and raw WebAssembly.promising tests
  did not reproduce the failure, consistent with Emscripten bookkeeping.
- Upstream main libpthread.js inspected on 2026-11-13 still lacked the
  pending-entry keepalive. Upstream issue #28258 was subsequently filed (see above).

Production integration:
- scripts/patch_jspi_pthread_entry.ts now retains the runtime before invoking
  the JSPI pthread entry and releases it in finally after await. This covers
  synchronous invocation errors and rejected promises. There is no await
  between releasing the keepalive and finish().
- Applied by scripts/patch_emscripten_runtime.mjs to browser and Node JSPI
  runtimes, including standalone solver packages. Asyncify is unchanged.
- Regression tests cover the forced callback ordering, synchronous errors,
  rejected promises, independently retained work, explicit exit/unwind,
  idempotence, and rejecting an unrecognized generated entry implementation.
- Temporary fixture response transforms and verbose progress hooks used
  during investigation have been removed. Integration tests use packaged
  runtime files directly.
- REPRO_KEEPALIVE remains the original diagnostic prototype used in the
  upstream report. REPRO_PRODUCTION_PATCH exercises the actual packaged fix.
  Do not combine those two controls.

At this earlier stage, the failure was isolated only to the
WebKit/Emscripten JSPI/pthread boundary. The follow-up above identifies the
Emscripten lifetime race.
The user chose further JSPI investigation over defaulting WebKit to Asyncify.
